# GuideLayout: Normalized Construction for Pillar/Condition Pages

**Status:** Design v6, 2026-06-08. CONVERGED after five `/arise --deep` traces (14 -> 13 -> 10 -> 3 -> 4 findings; pass 5 found ZERO HIGH/structural issues, only bookkeeping). v4 inverted the core model from "the layout re-emits each page's schema from typed props" to HYBRID PASSTHROUGH: the layout owns the registry-driven SEO foundation + uniform scaffolding; the page passes its schema through verbatim. v5 closed the three pass-4 mechanism findings the pivot exposed; v6 fixed the four pass-5 bookkeeping findings (the 7-vs-6 field count + `reviewer`-not-in-REQUIRED_FIELDS, the guides.json baseline-capture, the full-`<head>` comparator diff, the full-`Astro.props` forward set). Awaiting spec review then implementation plan.
**Owner:** Brian (RRM Academy)
**Scope:** `rrm-academy-cf`, pillar/condition guide pages.
**Verification base:** all claims re-checked against `origin/main` (13 pillars incl. isthmocele; validator has G1-G6 + `NON_PILLAR_CLINICAL`). A stale working branch (`claude/what-is-rrm-glossary-sync`, 12 pillars, no G6) produced three false-positive trace findings that do NOT apply to the real base.

## Problem

The 13 pillar/condition guides (`/what-is-rrm/`, `/naprotechnology/`, `/femm/`, `/neofertility/`, `/common-questions-about-rrm/`, `/glossary/`, `/art-registries-and-codes/`, `/rrm-success-rates/`, `/pcos/`, `/endometriosis/`, `/endometritis/`, `/miscarriage/`, `/isthmocele/`) are hand-authored 600-750 line `.astro` files cloned from one another. No single constructor guarantees their SEO foundation, so it drifts and can be forgotten entirely: `/isthmocele/` originally shipped with the generic fallback OG card, no `sitemap-pillars.xml` entry, and no `/guides/` listing because a manual clone bypassed the `ssot/guides.json` registry (since corrected: isthmocele is now registered, which is exactly the foundation a layout would have guaranteed from the start).

## Goals

1. A single `GuideLayout` owns the **SEO foundation that drifts or gets forgotten**: registry registration (so OG card + `sitemap-pillars.xml` + `/guides/` listing can never be skipped), `<title>`/meta-description/canonical/OG wiring, the breadcrumb, the byline, the TOC, the FAQ accordion, the disclaimer/cite band.
2. Normalize up means two things, both additive-only: (a) the **foundation/scaffolding** above is built one way for every pillar, replacing N hand-rolled variants; (b) the **rich domain schema** (the Article node and its `about`/`citation`/`image`/`wordCount`/`hasPart`, plus `FAQPage`/`ItemList`/`DefinedTermSet`) is **passed through verbatim**, never re-derived, so nothing a page emits today is dropped, reordered into a different value, or re-typed.
3. The foundation is single-sourced in `ssot/guides.json` (a true SSOT only after Phase 0; see "Reality check").
4. A gate makes the layout mandatory without ever deadlocking a deploy mid-rollout and without a missing flag silently exempting a page.
5. Visible content (body prose AND byline) is never changed by migration.

## Non-goals (YAGNI)

- No redesign / restyling of pillar bodies.
- No conversion of pillar prose or pillar JSON-LD into registry data; both stay in each page's `.astro`.
- No change to the library/commentary/FAQ/course dynamic templates.
- No new pillar content authored as part of this work.
- The layout does NOT take ownership of, normalize, or re-emit any page's domain schema node (Article core, `about`, `citation`, `image`, `wordCount`, `hasPart`, `FAQPage`, `ItemList`, `DefinedTermSet`). Those pass through.

## Reality check: what actually drifts, and why re-emission was the wrong model

Three traces established two things. First, the **foundation** is what drifts and is not yet single-sourced. Second (the pass-3 lesson), the **schema is too varied to re-model with typed props**: a layout that rebuilds the Article node from a prop list keeps dropping per-page properties. All claims below re-verified against `origin/main` source on 2026-06-08.

Foundation gaps to close in Phase 0:
- **Display fields are consumed visibly and disagree with what a naive layout would emit.** The `/guides/` cards render registry `author` (`guides/index.astro:30,90,100`) AND registry `description` (`guides/index.astro:29,89`). So reconciling the schema author or the meta description must NOT overwrite those registry strings, or the visible card changes. This is why the schema author needs a separate `authorId` and the meta description needs a separate `pageDescription` (the registry `author`/`description`/`title` stay as the card's display strings).
- **Title is up to four distinct strings; registry `title` is the card label, not the `<title>`.** Verified: for the 5 condition pillars registry `title` == page `<title>` == JSON-LD `headline`. For concept pillars they diverge (what-is-rrm: registry `title`="What is Restorative Reproductive Medicine?", `<title>`="What Is RRM? Restorative Reproductive Medicine", `headline`="What is Restorative Reproductive Medicine (RRM)?"). The layout needs a verbatim `pageTitle` for `<title>` distinct from registry `title`.
- **Meta description is a distinct string from the card description on >=6 pillars.** Verified: what-is-rrm page `<meta name="description">`="...Learn how RRM works." vs registry `description`="The diagnostic and treatment philosophy..." vs `og_description`="RRM diagnoses and treats root causes...". The layout needs a verbatim `pageDescription` for `<meta name="description">`/og:description, captured per page.
- **Author/reviewer byline has 5 DOM variants and femm's reviewer has no schema `@id`.** 4 pillars emit org-author + Naomi `reviewedBy` (glossary, art-registries, rrm-success-rates, isthmocele); 9 emit `author=#naomi-whittaker` with no reviewer; femm additionally renders a reviewer in the byline only (`erin-kay.webp` + "Reviewed by Erin Kay, DO", plain text, NOT linked) with NO schema `reviewedBy` and no `@id` for Erin Kay in the identity graph. So the byline is registry-driven display; the JSON-LD `author`/`reviewedBy` stay in the page's own schema (femm keeps no `reviewedBy`).
- **OG metadata stays BaseLayout-derived.** `BaseLayout` has no `ogTitle`/`ogDescription` prop; it derives `<meta og:title>` from the page title and `<meta og:description>` from the page description. The OG card PNG is registry-derived (`build-og-index.mjs` reads `og_title`/`og_description`). So the layout introduces NO `ogTitle`/`ogDescription` prop: og meta follows `pageTitle`/`pageDescription`, and the OG card index keeps reading `og_title`/`og_description` untouched.

Why the schema passes through verbatim (the pass-3 evidence that re-emission cannot win):
- 6 concept pillars emit `about:{MedicalTherapy}`, 5 condition pillars emit `about:{MedicalCondition}` with an ICD code, common-questions emits no `about`.
- rrm-success-rates citations append `url` (from a library slug) and `sameAs` (DOI) beyond the 4 stub fields; femm's `citation[]` contains a hand-authored `CreativeWork` node (Vigil 2019, string author) that a `ScholarlyArticle` stub would re-type.
- 4 pillars set `Article.image` (3 distinct URLs); per-page `wordCount` literals vary (14300/4900/3750/2900, glossary computed); art-registries' `articleSection` and `hasPart` are disjoint value-sets.
- art-registries emits an `ItemList` (~20 `CreativeWork`s, its primary payload); glossary emits a `DefinedTermSet` (132 `DefinedTerm` entities); common-questions builds its `FAQPage` via `buildFAQPage(...)`; endometritis hand-authors a `FAQPage` whose `acceptedAnswer.text` is independent prose, not a strip of the visible accordion.
- 3 pages (what-is-rrm, common-questions, art-registries) bundle everything in one `@graph`; the rest emit separate `<script type="application/ld+json">` blocks.

Re-modeling all of that with typed props is whack-a-mole (each trace found the next missing property). v4 stops trying: the page keeps authoring its schema object exactly as today and hands it to the layout untouched.

**Pillar taxonomy** (drives only the gate, not schema emission): clinical-schema pillars (those emitting `MedicalWebPage`/`MedicalCondition`) must be registered, enforced by the existing G6. `common-questions` emits bare `Article` and stays that way.

## Design

### `src/layouts/GuideLayout.astro`

Wraps `BaseLayout`; owns the foundation + uniform scaffolding; passes the page's schema through verbatim. The page supplies its body via slots and its JSON-LD via passthrough props.

**Props the layout consumes (resolved from `ssot/guides.json` by `slug` unless noted):**
- `slug` (required).
- `pageTitle` (BaseLayout `<title>`), `pageDescription` (BaseLayout `<meta name="description">` / og:description), `breadcrumbName` (the short crumb). All three captured verbatim per page in Phase 0. Registry `title`/`description`/`og_title`/`og_description` are untouched (card label, card description, OG-card index). No `ogTitle`/`ogDescription` prop; og meta follows `pageTitle`/`pageDescription` exactly as BaseLayout does today.
- `authorId` (`#organization` / `#naomi-whittaker` / other Person `@id`) and optional `reviewer` (`{ name, id? }`). These drive the **visible byline ONLY** (DOM + avatars), reproducing all 5 current variants from one parametric byline. They do NOT synthesize any JSON-LD `author`/`reviewedBy` node: that lives in the page's verbatim schema. femm passes `reviewer:{name:"Erin Kay, DO"}` (no `id`) and its schema keeps no `reviewedBy`, matching its current output.
- Avatars resolve per `@id` from a small id-to-path map (Phase 0, seeded from the current hardcoded byline `<img src>`s: `#naomi-whittaker`->`/images/authors/naomi-whittaker.webp`, femm reviewer Erin Kay->`/images/authors/erin-kay.webp`, `#organization`->the org apple-touch-icon), with an initials fallback for any `@id` with no mapped avatar.

**Props the layout passes through (the page authors these; the layout preserves every node byte-equal):**
- `jsonLd` (the page's domain schema: the Article/MedicalWebPage node with its `headline`/`author`/`reviewedBy`/`about`/`citation`/`image`/`wordCount`/`hasPart`/`articleSection`/`mainEntityOfPage`/`datePublished`/`dateModified`/`speakable`). Forwarded to `BaseLayout`'s existing `jsonLd` prop. The invariant is NODE-level, not object-level: the layout preserves each domain node byte-equal, but a page MAY re-partition its nodes between `jsonLd` and `extraSchema` during migration (see the `@graph` rule below).
- `extraSchema?` (`object[]`): additional verbatim JSON-LD nodes emitted as separate `<script type="application/ld+json">` blocks: glossary's `DefinedTermSet` (already a standalone block today, the clean example), endometritis' `FAQPage`, and any future bespoke node. The page builds these; the layout only relays them.
- **`@graph` decomposition (the 3 bundled pages: what-is-rrm, common-questions, art-registries).** These emit Article + BreadcrumbList + FAQPage/ItemList inside one `@graph` object today, passed whole as `jsonLd`. Migration DECOMPOSES that `@graph`: the Article/MedicalWebPage node becomes the top-level `jsonLd`, the FAQPage/ItemList nodes become `extraSchema[]` entries, and the in-`@graph` BreadcrumbList is DELETED (the layout re-emits it). This is the single accepted per-page schema rewrite; the comparator asserts node-level byte-equality and treats the BreadcrumbList page->layout move as the one sanctioned removal+re-add. So "passthrough" means every domain node is preserved byte-equal, NOT that the `jsonLd` container object is forwarded untouched.
- **BaseLayout passthrough props.** The layout forwards the FULL BaseLayout `Astro.props` destructure set (`BaseLayout.astro:70-88`), not a hand-listed subset, so the implementer codes the forward map from BaseLayout's actual prop list rather than an enumeration that can drift. The props pillars actually set today: `canonicalUrl` (all 13), `ogType` + `publishDate` (all 13, via `ogType="article"`), `speakable`, `chrome`, `trackScroll` (7 pillars; drives the `<body data-track-scroll-page>` scroll-depth GA4 signal), `markdownUrl` (glossary only; drives the `<link rel="alternate" type="text/markdown">` agent surface); plus `ogImage`/`noindex`/`lastModified`/`citationMeta`/`bodyClass` if a future page sets them. `canonicalUrl` is special: if not forwarded, BaseLayout silently falls back to `Astro.url.href` and emits a wrong canonical + og:url + hreflang triple with no error, so it must be relayed. The page passes what it passes today; the layout relays it. These stay page render-props (NOT registry fields); the comparator asserts the full BaseLayout-emitted `<head>` + `<body>` surface is unchanged.

**Props that drive scaffolding DOM (not schema):**
- `pageH1` (the `<h1>` text): the layout renders the page `<h1>` from it (migrated pages have no literal `<h1>` in their body). Captured verbatim in Phase 0. This is ALSO the value `build-guides-data.mjs` reads for the `/guides/` card title (the card title is the `<h1>` today, NOT `pageTitle`; the two differ on 6 concept pillars).
- `faqs?` (`{question, answerHtml}[]`): renders the **visible FAQ accordion DOM only**. The `FAQPage` JSON-LD is whatever the page already authored (in `jsonLd` or `extraSchema`), so there is no answer-text round-trip to preserve. Omitted on pages with no accordion (common-questions renders no accordion; its `FAQPage` rides in `extraSchema`).
- `tocItems?` (`{href,label}[]`): drives mobile TOC, `SectionTocChips`, sidebar `.toc`. Optional.
- `keyTakeaways?` (HTML[]); `disclaimer?` (HTML, defaults to the canonical condition-page text but every migrated page passes its existing disclaimer verbatim, 4 known variants); `editingNotice?` (bool); `disambig?` (HTML); `citeThisPage?` (bool/props). First-class so migration cannot drop them.
- Shell/scaffolding opt-outs: `hasRail?` + forwarded `<slot name="rail">` (glossary's A-Z rail); `pagefindIgnore?` / `showToc?` / `showCite?` / `showPdf?` for the concept outliers.

**Body:** default `<slot>` for prose + card grids; named `rail` slot forwarded into the inner `MaybeShell`.

**JSON-LD the layout itself emits (the ONLY node it owns):**
- `BreadcrumbList` (Home > Guides > `breadcrumbName`), uniform across all pillars. For separate-block pages it replaces the page's standalone BreadcrumbList block; for the 3 `@graph` pages it replaces the deleted in-graph BreadcrumbList node. The comparator asserts the emitted `BreadcrumbList` is equivalent to the page's current one AND that exactly one BreadcrumbList exists post-migration. Everything else (`jsonLd` + `extraSchema`) is page-authored passthrough.

**Foundation the layout emits:** `BaseLayout` (title from `pageTitle`, description from `pageDescription`, plus every other BaseLayout prop the page sets, forwarded); the `<h1>` (from `pageH1`); the breadcrumb nav; the byline DOM (from `authorId`/`reviewer` + avatar map); the TOC trio; the FAQ accordion DOM (from `faqs`); `LastUpdated`; disclaimer; `CiteThisPage`; `MaybeShell` + rail; plus the `extraSchema` blocks relayed verbatim.

### Registry coupling (Phase 0)

Extend each `ssot/guides.json` entry with 7 new fields: 6 REQUIRED (`pageTitle`, `pageDescription`, `pageH1`, `breadcrumbName`, structured `authorId`, and a per-slug `usesGuideLayout` boolean defaulting false) plus 1 OPTIONAL (`reviewer`, present on the 4 org-author pillars + femm, absent on the 9 others). Capture `pageTitle`/`pageDescription`/`pageH1`/`breadcrumbName`/`authorId`/`reviewer` verbatim from each page's current source. `pageH1` (the page `<h1>` text) is distinct from `pageTitle` (the `<title>`): they differ on 6 concept pillars, and `pageH1` (not `pageTitle`) is the string the `/guides/` card uses. Leave the display `author`/`description`/`title`/`og_title`/`og_description` strings untouched (guides card metadata + OG-card index). Seed the avatar id-to-path map (a layout-side constant, not a per-entry field).

Because the layout no longer rebuilds the `about` node, the registry needs NO `condition`/`conditionName`/`icd10`/`icd10System` fields, and there is no G8: the `MedicalCondition`/`MedicalTherapy` node stays in the page's verbatim `jsonLd`. The existing G6 already guarantees clinical pages are registered.

The 6 REQUIRED new fields (`pageTitle`/`pageDescription`/`pageH1`/`breadcrumbName`/`authorId`/`usesGuideLayout`) are static authoring fields present on every entry from the Phase 0 commit, so they go into `REQUIRED_FIELDS` in the SAME commit (closing the "a new pillar born without `usesGuideLayout`/`authorId` is silently un-enforced" hole). `reviewer` is NOT added to `REQUIRED_FIELDS`: `gateG1` fails on any `=== undefined` field, and 9 pillars legitimately have no reviewer, so adding it would deadlock Phase 0. There is no `pillars.schema.json` and `ssot:validate` does not read `guides.json` (verified: `docs/schemas/` does not exist; `npm run ssot:validate` runs `tools/site-ssot/bin/ssot-validate.mjs` over the site/organization/services/agent-surfaces files). The ONLY registry validator is `scripts/gates/validate-guides-registry.mjs` (the hard, deploy-blocking step at `deploy.yml:72`, currently G1-G6 incl. `NON_PILLAR_CLINICAL`). Phase 0 updates that one validator only, atomically.

**Build-script reconciliation (mandatory, same Phase 0/1 window).** `scripts/build-guides-data.mjs` currently SCRAPES each page's `<h1>` and `<BaseLayout ...>` from source via regex and `process.exit(1)` if absent. A migrated page has neither literal (GuideLayout renders the H1 and wraps BaseLayout internally), so the first migrated page would hard-fail `npm run build`. Refactor `build-guides-data.mjs` to source the card `title` from registry `pageH1` (the exact value the current `<h1>` scrape produces, NOT `pageTitle`: the two differ on 6 concept pillars, and the card title is fed to the Vectorize embedder 3x, so substituting `pageTitle` would silently shift that page's semantic-search ranking) and `description` from registry `pageDescription` (which equals the current `<BaseLayout description>` scrape) for any pillar whose `usesGuideLayout` is true, falling back to the current scrape for un-migrated pages. Add to the build-green checklist: `guides.json` entry count == `pillars.length` AND, per migrated slug, `guides.json[slug].title`/`description` byte-equal to the pre-migration scraped value.

### Gate (flag-based, never deadlocks; enforces SCAFFOLDING, not schema literals)

- Keep **G6** (a clinical-schema root page must be registered or in `NON_PILLAR_CLINICAL`).
- **G7 (new, flag-based):** drive enforcement off `usesGuideLayout`, resolved via the registry `file` field (so it handles the root-file pillar `common-questions-about-rrm.astro`):
  - `usesGuideLayout` and `authorId` are in `REQUIRED_FIELDS`, so a missing flag fails G1 before G7 runs (no undefined-equals-skip exemption).
  - every slug with `usesGuideLayout:true` MUST import `GuideLayout` (anchored regex `/^\s*import\s+GuideLayout\s+from/m`, not a substring `includes()`), and MUST NOT import or use `BaseLayout` directly (anchored `import ... BaseLayout` regex + no `<BaseLayout` tag) and MUST NOT hand-roll a `BreadcrumbList` literal (the one node the layout owns).
  - every slug with `usesGuideLayout:false` MUST NOT import `GuideLayout` (anchored regex; catches half-reverts).
  - G7 does NOT ban `Article`/`MedicalWebPage`/`MedicalCondition`/`MedicalTherapy`/`FAQPage`/`ItemList`/`DefinedTermSet` literals: those are the page's legitimate verbatim passthrough (`jsonLd`/`extraSchema`), including the nodes the 3 `@graph` pages decompose into `extraSchema`. Banning them would deadlock those pages. The BreadcrumbList ban IS satisfiable because every page, separate-block or decomposed-`@graph`, ends with no standalone and no in-graph BreadcrumbList literal of its own (the layout owns it).
- No G8 (no condition fields to gate; `about` is verbatim).
- Because `usesGuideLayout` is false for all pillars at Phase 0/1 and flips atomically per migration, the gate is green at every commit.

### Verification (semantic, not textual; built in Phase 1)

A textual diff is unrunnable (`safeJsonLd` does not sort keys). Use a semantic comparator, run per migrated page:
- Parse EVERY `application/ld+json` block (the page's `jsonLd`, every `extraSchema` block, and the layout's `BreadcrumbList`) and flatten to one node map keyed by `@id` when present else `(@type, headline|name)`. Compare at the NODE level, NOT the container-object level (so an `@graph` decomposition into separate blocks is not flagged as a change): every pre node must reappear post, byte-equal, with no changed values and no `@id` synthesized that the source lacks. The ONE sanctioned change is BreadcrumbList moving page->layout (a removal of the page's node + re-add of the layout's equivalent one); assert exactly ONE BreadcrumbList node exists post-migration (catches the duplicate-BreadcrumbList failure mode on `@graph` pages).
- Assert the ENTIRE BaseLayout-emitted `<head>` (every `<meta>`/`<link>`/`<title>`) plus the `<body>` attributes are unchanged via an allowlist-free normalized diff (not a hand-enumerated subset, so any future BaseLayout-prop output is covered without re-listing). This necessarily includes `<title>`, `<meta name="description">`, og:title/og:description/og:type/og:image, canonical + the hreflang triple, speakable, `noindex`, `<link rel="alternate" type="text/markdown">` (glossary's `/glossary.md`), the `publishDate`/`lastModified`-derived `article:published_time` / `article:modified_time` / `last-modified` tags, and the `<body data-track-scroll-page>` attribute. (`<title>` catches the `pageTitle` case; `<meta name="description">` the `pageDescription` case; the rest catch the dropped-BaseLayout-prop class.)
- Assert `guides.json[slug].title` and `.description` are byte-equal pre/post (catches the `build-guides-data` `pageH1`-vs-`pageTitle` Vectorize-embedding leak; the count gate alone misses it). `guides.json` is gitignored and rebuilt, so the `pre` baseline must be BUILT, not read from git and NOT read from the registry `pageH1` (that would tautologically pass): before the migration commit, run `node scripts/build-guides-data.mjs` against the un-migrated page (the comparator already checks out / holds the pre-migration source for the schema and `<title>` assertions), snapshot `guides.json[slug].title`/`.description`, then assert the post-migration rebuild matches that snapshot.
- Compare the byline by normalized **outerHTML** (whitespace-collapsed), not just `textContent`, so a changed avatar count / link wrapping / reviewer DOM is caught; also assert the byline's author/reviewer is consistent with the verbatim schema's `author`/`reviewedBy` `@id`s (femm: byline shows a reviewer the schema lacks, which is its current state and must be reproduced, not "fixed").
- Assert `sitemap-pillars.xml` + `/guides/` listing + OG index entry unchanged (all 13 are already registered, so migration adds no surface).
- Body prose checked unchanged via Playwright desktop + mobile (393x852) screenshots.

### Deploy choreography

Each migration ships via the standard worktree-off-`origin/main` -> `claude/*` -> auto-merge -> deploy. No per-slug OG purge: the OG card index reads registry `og_title`/`og_description`, untouched by migration, so cards are byte-identical and no `OG_VERSION` bump is needed.

## Rollback

Revert the entire migration commit (page `.astro` AND its `usesGuideLayout` flag together), never the page alone, which would leave the flag true and re-trip G7. The bidirectional G7 check (flag<->import must agree) catches a partial revert locally before push. Phase 0, the layout file, and the `build-guides-data.mjs` refactor are additive and inert for un-migrated pages.

## Risks

- **Layout bug across pages** -> mitigated by the 7-page proof covering every passthrough + scaffolding edge before waves + per-page semantic verification.
